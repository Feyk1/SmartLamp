# ADR-010 — JWT for the dashboard and opaque token for the firmware

- **Date:** 2026-11-18
- **Status:** Accepted
- **Decision makers:** Project maintainer
- **Project context:** The orchestrator must authenticate two types of clients with very different characteristics: the dashboard (browser, human user) and the firmware (C process, limited resources).

## Context

The orchestrator exposes:

- **REST and WebSocket for the dashboard:** queries, commands, historical telemetry, fault injection.
- **REST and WebSocket for the firmware:** telemetry, OTA download, command reception.

Both channels need authentication, but the clients have different constraints:

| Characteristic | Dashboard | Firmware |
| :--- | :--- | :--- |
| **Language** | JavaScript (browser) | C (POSIX, limited resources) |
| **Ability to parse a JWT** | Trivial (`jwt-decode`, standard libraries) | Costly (base64url + JSON + HMAC-SHA256 in C) |
| **Ability to verify signatures** | Trivial (Web Crypto API) | Costly (requires `mbedtls` or `libsodium`) |
| **Session duration** | 1 h (instance lifetime) | Instance lifetime |
| **Token exposure** | Visible in the browser DevTools | Never visible outside the instance |
| **Need for claims** | Yes (`instance_id`, `role`, `exp`) | No (identification only) |
| **Rotation** | By expiration (1 h) | By instance destruction |

Three schemes were evaluated:

1. **JWT for both** (dashboard and firmware).
2. **Opaque token for both** (table lookup for both).
3. **JWT for the dashboard + opaque token for the firmware** (hybrid).

## Decision

**The hybrid is chosen:**

- **Dashboard:** `session_token` as a **JWT HS256** with claims `sub`, `instance_id`, `role`, `iat`, `exp`, `jti`.
- **Firmware:** `device_token` as an **opaque 32-byte hex token** (64 characters), generated by the orchestrator when the instance is created, injected into the Machine as an environment variable, validated with a table lookup + constant-time comparison.

The `device_token` **is never exposed to the browser**. Only the orchestrator and the ephemeral Machine know it.

## Alternatives considered

### Alternative A: JWT for both

**Advantages:**
- **A single mechanism:** the orchestrator has a single authentication middleware.
- **Stateless:** it does not require a table lookup; the signature and `exp` are enough to validate.
- **Rich claims:** the firmware could include additional information (version, capabilities) in the JWT.
- **Standardized:** JWT is a widely adopted standard (RFC 7519).

**Drawbacks:**
- **Costly parsing in C:** the firmware needs to decode base64url, parse JSON and verify HMAC-SHA256. It requires `mbedtls` or `libsodium`, which adds ~500 KB to the binary.
- **Signature verification on every request:** the firmware must verify the HMAC signature on every REST request and every WS message, which consumes CPU and increases latency.
- **The firmware does not need claims:** the `device_token` only identifies the instance; there is no additional information the firmware needs to read.
- **Risk of error:** implementing HMAC-SHA256 in C from scratch is prone to bugs; using a library adds a dependency.
- **The token is longer:** a typical JWT has ~200-300 characters vs. 64 for the opaque token, which increases the size of requests and logs.

**Discarded because:** the cost of parsing and verification in C provides no benefit (the firmware does not need claims), and it adds dependencies and error surface.

### Alternative B: Opaque token for both

**Advantages:**
- **A single mechanism:** the orchestrator has a single authentication middleware (table lookup).
- **Simple:** it does not require JWT parsing or signature verification.
- **Revocable:** deleting the table entry invalidates the token immediately.
- **Short tokens:** 64 characters vs. ~300 for a JWT.

**Drawbacks:**
- **Stateful:** it requires a table lookup on every request, which adds latency and couples the orchestrator to its storage.
- **No claims:** the dashboard needs `instance_id` and `role`; with an opaque token, that data must be obtained with an additional lookup (or included in the `POST /instances` response).
- **No native expiration:** the orchestrator must manage the TTL manually (delete the entry after 1 h), which adds code.
- **No `jti`:** a session cannot be correlated with an audit log without an additional identifier.

**Discarded for the dashboard because:** the dashboard benefits from the claims (`instance_id`, `role`, `exp`) and from the JWT's native expiration. The table lookup adds unnecessary latency.

### Alternative C: JWT for the dashboard + opaque token for the firmware (chosen)

**Advantages:**
- **Each mechanism adapts to its client:** JWT for the browser (where parsing and verification are trivial), opaque token for the firmware (where parsing and verification are costly).
- **Stateless for the dashboard:** the JWT includes `instance_id` and `role`, which avoids table lookups.
- **Stateful for the firmware:** the table lookup is trivial (one entry per instance) and allows immediate revocation.
- **No cryptographic dependencies in the firmware:** the firmware only compares strings with a constant-time `memcmp`; it does not need `mbedtls` for authentication.
- **Short tokens in the firmware:** 64 characters vs. ~300 for a JWT, which reduces the size of logs and requests.
- **`device_token` never exposed to the browser:** the dashboard never sees the firmware token, which reduces the attack surface.

**Drawbacks:**
- **Two mechanisms:** the orchestrator has two authentication middlewares (JWT and lookup).
- **Two issuance flows:** `POST /instances` issues both tokens (JWT for the dashboard, opaque for the firmware).
- **Two validation flows:** JWT in dashboard endpoints, lookup in firmware endpoints.

**Chosen because:** the balance between simplicity, security and adaptation to the client is the best.

## Consequences

### Positive

- **No cryptographic dependencies in the firmware:** the firmware only compares strings; it does not need `mbedtls` for auth (although it does for OTA).
- **Stateless for the dashboard:** the JWT includes `instance_id` and `role`, which avoids table lookups.
- **Immediate revocation for the firmware:** deleting the table entry invalidates the token.
- **`device_token` never exposed to the browser:** the dashboard never sees the firmware token.
- **Short tokens in the firmware:** 64 characters vs. ~300 for a JWT.
- **Auditing:** the JWT's `jti` allows correlating a session with a log.

### Negative

- **Two middlewares:** the orchestrator has two authentication flows, which adds code.
- **Two issuance flows:** `POST /instances` issues both tokens, which adds complexity.
- **Risk of confusion:** a developer could use the `device_token` in a dashboard endpoint or vice versa. Mitigation: the middlewares are different and the endpoints are separated by prefix (`/api/v1/` vs. `/api/v1/device/`).

### Neutral

- **The `device_token` is injected as an env var:** when creating the Machine, the orchestrator passes `DEVICE_TOKEN` as an environment variable.
- **The `session_token` is returned in `POST /instances`:** the dashboard stores it in `sessionStorage`.
- **`JWT_SECRET` lives in Fly Secrets:** the orchestrator uses it to sign and verify JWTs.
- **The `device_token` lives in the orchestrator's memory:** it is generated when the instance is created and deleted when it is destroyed.

## Implementation notes

### `session_token` claims

```json
{
  "sub": "session-abc123",
  "instance_id": "inst-8f2a",
  "role": "user",
  "iat": 1705312200,
  "exp": 1705315800,
  "jti": "uuid-v4"
}
```

- `role` ∈ `{"user", "sim"}`.
- `exp` = `iat` + 3600 (1 h).
- `jti` = UUID v4 for auditing.

### Token issuance

```python
# backend/src/auth/tokens.py
import secrets, uuid
from datetime import datetime, timedelta
import jwt

def issue_tokens(instance_id: str, role: str) -> tuple[str, str]:
    # 1. JWT for the dashboard
    now = datetime.utcnow()
    session_token = jwt.encode(
        {
            "sub": f"session-{uuid.uuid4().hex[:8]}",
            "instance_id": instance_id,
            "role": role,
            "iat": now,
            "exp": now + timedelta(hours=1),
            "jti": str(uuid.uuid4()),
        },
        JWT_SECRET,
        algorithm="HS256",
    )
    # 2. Opaque token for the firmware
    device_token = secrets.token_hex(32)  # 64 hex characters
    return session_token, device_token
```

### `session_token` validation

```python
# backend/src/auth/middleware.py
async def require_session(request, call_next):
    token = extract_bearer(request)
    try:
        claims = jwt.decode(token, JWT_SECRET, algorithms=["HS256"])
    except jwt.ExpiredSignatureError:
        raise HTTPException(401, "TOKEN_EXPIRED")
    except jwt.InvalidTokenError:
        raise HTTPException(401, "INVALID_TOKEN")
    request.state.session = claims
    return await call_next(request)
```

### `device_token` validation

```python
# backend/src/auth/middleware.py
async def require_device(request, call_next):
    token = extract_bearer(request)
    instance = instances_by_device_token.get(token)
    if instance is None:
        raise HTTPException(401, "INVALID_DEVICE_TOKEN")
    # Constant-time comparison (although the lookup is already O(1))
    if not secrets.compare_digest(token, instance["device_token"]):
        raise HTTPException(401, "INVALID_DEVICE_TOKEN")
    request.state.instance = instance
    return await call_next(request)
```

### Validation in the firmware (C)

```c
// firmware/src/comms/auth.c
int validate_device_token(const char *token, const char *expected) {
    // Constant-time comparison to avoid timing attacks
    size_t len = strlen(token);
    if (len != strlen(expected)) return -1;
    unsigned char diff = 0;
    for (size_t i = 0; i < len; i++) {
        diff |= token[i] ^ expected[i];
    }
    return diff == 0 ? 0 : -1;
}
```

- The firmware **does not parse JWTs**: it only compares the `device_token` with the expected value (which it receives as an env var at startup).
- The comparison is constant-time to avoid timing attacks (although in practice the risk is low, it is a good practice).

### Endpoints separated by prefix

| Prefix | Middleware | Client |
| :--- | :--- | :--- |
| `/api/v1/` | `require_session` (JWT) | Dashboard |
| `/api/v1/device/` | `require_device` (lookup) | Firmware |
| `/ws/dashboard` | `require_session` (query string) | Dashboard |
| `/ws/device` | `require_device` (query string) | Firmware |
